Dexie vs localStorage

How browser storage works, with process flows, examples, advantages and disadvantages

Technical briefing · Independent of any specific product · August 2026

Purpose. This document explains two common ways a web app can keep data on the user’s device: the browser’s built-in localStorage API, and Dexie.js (a library on top of IndexedDB). Examples use a bookstore kiosk and a school attendance app — not a restaurant POS.

1. What problem they solve

A normal website forgets everything when the tab closes, unless data is stored somewhere. The server can store it, but the device can also store it locally. Local storage is useful when:

  • The network is slow or missing (a shop on a weak connection, a classroom with no Wi‑Fi).
  • The app must open instantly with last-used data (cart, draft form, last page).
  • The same browser should remember settings (language, theme, last school selected).

localStorage and Dexie / IndexedDB both live in that browser, on that computer. They are not a cloud database. Clearing site data, using another browser, or another device means the data is not there.

2. How localStorage works

2.1 What it is

localStorage is a small key–value store built into every modern browser. You save a string under a name (the key). Later you read that string back. There are no tables, no indexes, and no query language. If you need an object or a list, you convert it to JSON text first.

Typical limits: about 5 MB per site (varies by browser). Storage is synchronous: the JavaScript thread waits until the read or write finishes.

2.2 The process, step by step

User taps “Save draft” │ ▼ App builds a JavaScript object { studentId: "S104", present: true } │ ▼ JSON.stringify(...) → '{"studentId":"S104","present":true}' │ ▼ localStorage.setItem("attendance-draft", thatString) │ ▼ Browser writes the string into its site storage (disk / profile folder). The call returns only when done. ----- later, even after closing the tab ----- App starts │ ▼ localStorage.getItem("attendance-draft") │ ▼ JSON.parse(...) → original object │ ▼ Form is filled again

2.3 Worked example — bookstore shopping cart

A customer adds books at a library kiosk. The kiosk should keep the cart if the page reloads.

  1. Customer adds “The Alchemist”, quantity 2.
  2. The app holds an array in memory: [{ isbn: "978...", qty: 2 }].
  3. It stringifies the array and saves it as key bookstore-cart.
  4. Power flickers; the page reloads. On startup the app reads bookstore-cart, parses JSON, and shows two copies of the book.
  5. At checkout, the app sends the cart to the server. After success it can removeItem("bookstore-cart").
What localStorage cannot do well here. You cannot ask “all cart lines where qty > 1” inside the database. You must load the entire string, parse it, then filter in JavaScript. For one cart that is fine. For 50,000 book records it is slow and can freeze the screen.

sessionStorage is the same API but is cleared when the tab closes. This document focuses on localStorage (survives close/reopen of the browser).

3. How Dexie (IndexedDB) works

3.1 What it is

IndexedDB is the browser’s built-in database for larger, structured data. It stores objects (not only strings), supports indexes, and works asynchronously so the UI can stay responsive.

The raw IndexedDB API is verbose (callbacks, version upgrades). Dexie.js is a small open-source library that wraps IndexedDB with a simpler, Promise-based API: define tables, then add, put, get, where(...).equals(...).

Typical quota is much larger than localStorage — often hundreds of MB or more, depending on disk and browser policy.

3.2 The process, step by step

App starts │ ▼ new Dexie("school-attendance") .version(1).stores({ students: "id, classCode, name", marks: "++id, studentId, date" }) │ ▼ Browser opens (or creates) an IndexedDB named "school-attendance" with two object stores and indexes on classCode, name, studentId, date. Teacher marks S104 present │ ▼ db.marks.add({ studentId: "S104", date: "2026-08-18", present: true }) │ ▼ Dexie starts an IndexedDB readwrite transaction │ ▼ Browser writes a record to disk in the background │ ▼ Promise resolves → UI shows “saved” (the page was not frozen while waiting) ----- later: “who was absent in class 8A today?” ----- db.students.where("classCode").equals("8A").toArray() │ ▼ Only matching student rows are read (index), not the whole database │ ▼ Then query marks by studentId + date and combine in the app

3.3 Worked example — school attendance

A teacher’s tablet keeps the class list even if the school Wi‑Fi drops.

  1. On first online login, the app downloads 800 students and stores them with Dexie: one row per student, indexed by classCode.
  2. During the day the network fails. The teacher still opens class 8A. Dexie reads only those students via the index.
  3. Each tap (“present” / “absent”) inserts a row in the marks table. That is one small write, not rewriting a giant JSON blob.
  4. When Wi‑Fi returns, the app reads unsynced mark rows (for example where synced === false) and POSTs them to the school server.
  5. After the server confirms, those rows are updated to synced: true — or deleted from the local queue table.
Why Dexie fits this example. Thousands of students, many mark events, search by class, and background writes. That is a database job. Doing the same with one localStorage string would mean parse-all / stringify-all on every tap.

3.4 What Dexie adds on top of IndexedDB

  • Declare schema and indexes in a few lines.
  • Version upgrades when you add a table or index.
  • Promises / async-await instead of nested callbacks.
  • Queries: equals, startsWith, between, bulk put/delete.
  • Optional live queries (UI updates when the table changes) if you use the Dexie React bindings — not required.

Dexie does not replace the server. It is still on-device storage. Sync to a server is your own code (HTTP, outbox, and so on).

5. Complete advantages and disadvantages

5.1 localStorage — advantages

  1. Zero dependency. Built into the browser. No npm package, no version upgrade of a library.
  2. Trivial API. Two methods cover most needs: setItem and getItem.
  3. Synchronous and easy to reason about. After setItem returns, the value is there. No Promises, no “did the transaction commit?”.
  4. Perfect for tiny flags. Language, theme, “don’t show this tip again”, last selected branch/school id, a short draft.
  5. Easy to debug. Chrome DevTools → Application → Local Storage. You see keys and values as text.
  6. Works in all modern browsers, including older ones that developers still meet on kiosks.
  7. Same-origin isolation. Site A cannot read site B. Simple security boundary (still never store passwords or card PANs).
  8. Survives refresh and browser restart until the user or the app clears it.

5.2 localStorage — disadvantages

  1. Strings only. Numbers, dates, arrays, and objects must be JSON-encoded. Easy to corrupt with a bad parse.
  2. No queries or indexes. Any “find by field” means load everything.
  3. Rewrite the whole blob to change one field inside a stored array.
  4. Small quota (~5 MB). Photos, catalogues, or long history will fail.
  5. Synchronous = can freeze the UI on large JSON parse/stringify.
  6. No transactions. If the tab dies in the middle of two related setItem calls, data can be half-updated.
  7. No schema. Old keys linger. Migrations are homemade (“if version < 2, reshape JSON”).
  8. Shared across tabs, but with races. Two tabs writing the same key can overwrite each other. The storage event notifies other tabs, but you still merge by hand.
  9. Not for secrets. Any script on the page (including XSS) can read it. Not encrypted at rest by the app.
  10. Blocking on the main thread is a problem inside service workers / strict performance budgets; some environments discourage large localStorage use.
  11. Private / strict browsers may evict or limit it more aggressively.

5.3 Dexie — advantages

  1. Real database on the device. Rows, primary keys, secondary indexes.
  2. Async I/O. The page stays interactive while reading or writing.
  3. Partial updates. Change one attendance mark without rewriting the whole class list.
  4. Queries. Filter by indexed fields instead of loading the world.
  5. Much larger storage than localStorage — suitable for catalogues, logs, offline queues with many ops.
  6. Transactions. Several table writes succeed or fail together (safer than two separate setItems).
  7. Versioned schema. You can add an index in version 2 and migrate existing data.
  8. Bulk operations (bulkPut, bulkDelete) for first-time download of a master list.
  9. Friendlier than raw IndexedDB. Less boilerplate, fewer footguns around versionchange events.
  10. Good fit for offline-first apps that later sync: keep a local table of pending operations, query status === "pending".
  11. Works with large object graphs (nested objects, arrays) without manual stringify of the entire DB.

5.4 Dexie — disadvantages

  1. Extra library. Bundle size, licensing (Apache-2.0), and you must keep the package updated.
  2. Async everywhere. Callers must use await / .then(). Easy to show stale UI if you forget to wait.
  3. Steeper learning curve than setItem: schema, indexes, compound keys, upgrade functions.
  4. Schema mistakes are costly. A wrong index means a new version and a migration. IndexedDB version upgrades can fail if another tab is open.
  5. Harder to inspect. DevTools IndexedDB viewer is less obvious than a JSON string in localStorage.
  6. Still origin-scoped and still not a server. No multi-device sync unless you build it.
  7. Not encrypted by default. Same XSS warning as localStorage: page JavaScript can read the DB.
  8. Browser quirks. Safari / private mode historically evicted IndexedDB; quota prompts differ by vendor.
  9. Overkill for three flags. Opening a DB to store theme=dark is unnecessary complexity.
  10. Indexes only help if you planned them. Querying an unindexed field still means a table scan.
  11. Debugging transactions (AbortError, ConstraintError, VersionError) is harder than a failed setItem.
  12. SSR / Node has no IndexedDB unless you polyfill. localStorage also needs a window, but tests often mock it more easily.

7. How people combine them (generic pattern)

Many apps use both, on purpose:

  • localStorage: “current language”, “last school id”, “device nickname” — tiny, read at startup before any async DB is open.
  • Dexie: students, products, pending sync operations — anything with many rows.
App boot 1. Read localStorage "lang" and "lastSchoolId" ← instant, sync 2. Open Dexie database ← async 3. Load class list from Dexie 4. If online, fetch server updates and bulkPut 5. If offline, keep teaching; queue new marks in a Dexie table 6. When online again, send pending rows, then mark them synced

A weaker (but common) pattern is dual-write: save the same list into Dexie and a localStorage JSON copy so old code that only knows getItem still works. That wastes space and can drift if one write fails. Prefer one source of truth per kind of data.

9. Security and operations (both technologies)

  • XSS: if malicious script runs on your origin, it can read localStorage and IndexedDB. Storage choice does not fix XSS.
  • Shared computers: a bookstore kiosk should wipe or use a locked-down profile; otherwise the next customer can open DevTools.
  • Backup: neither is a backup. Export to a file or sync to a server if the device can be lost.
  • Clearing site data in the browser deletes both.
  • Incognito: data may vanish when the window closes.

10. Short recap

localStorage

A named box of text. Save a string, read a string. Fast to learn, easy to debug, small and synchronous. Use it for settings and tiny drafts. Do not use it as a database.

Dexie

A friendly API over IndexedDB. Tables, indexes, transactions, async writes. Use it when the device must hold and search real records, especially offline. It is still local to that browser.

Rule of thumb: if the data is one key you could write on a sticky note, use localStorage. If it looks like a spreadsheet with many rows you would filter, use Dexie.

This briefing is educational. Browser quotas and DevTools labels change by vendor and version. Dexie.js is a third-party wrapper around the W3C IndexedDB standard; localStorage is part of the Web Storage standard.
